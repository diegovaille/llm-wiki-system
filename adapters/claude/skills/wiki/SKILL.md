# Wiki skill

Durable project knowledge lives at `/Users/diegovaille/Git/wiki/<project>/`. Use the `wiki` CLI to interact with it. Never ad-hoc grep into wiki pages — always use `wiki query`.

## Binary (absolute path — NOT on PATH)

```
/Users/diegovaille/Git/wiki-system/.venv/bin/wiki --config /Users/diegovaille/Git/wiki/wiki.config.toml
```

In all slash commands below, `WIKI` refers to that absolute invocation.

## Project detection

The `wiki` CLI takes a `<project>` argument. Detect the current project by matching the current working directory against `[[projects]] repo_path` in `/Users/diegovaille/Git/wiki/wiki.config.toml`. If no project matches, the current repo is NOT wiki-enabled — tell the user and stop.

## Retrieval contract

- To answer a question with compiled knowledge, run `/wiki-query` (wraps `WIKI query <project> "<question>"`).
- The command returns top-ranked pages with match reasons and snippets. Read the top 1-3 pages via `Read` before answering.
- Fall back to raw project docs only when the wiki does not answer.

## Capture threshold (under-capture bias)

`/wiki-capture` distills session learning into at most ONE canonical change (noop, update, or create). Capture only when:

- a non-obvious decision was made
- a reusable pattern emerged
- a debugging lesson is likely to recur
- an important assumption changed
- a project concept became clearer than the docs currently state

Do NOT capture routine implementation, obvious bug fixes, small refactors, or transient exploration. Default to no-op. When in doubt, prefer update over create.

## Six operations

1. `WIKI query` — deterministic retrieval (lexical + link-graph)
2. `WIKI index` — rebuild retrieval index + regenerate views
3. `WIKI capture prepare` / `WIKI capture submit` — session/tacit learning → staged proposal
4. `WIKI promote` — the only path from staging to pages
5. `WIKI review` (via `/wiki-review`) — list pending staged items
6. `WIKI sync` — (v0.2) artifact registration

## Prepare/submit protocol

Generative operations use a two-step protocol:

1. The core CLI runs `WIKI capture prepare` and emits a JSON prompt package with `{ system, context, schema, instructions, allowed_actions }`
2. You (Claude) reason over it and produce a structured proposal matching `allowed_actions` and the schema
3. The core CLI runs `WIKI capture submit --proposal=-` to validate and write a `state: proposed` staged file

You never write to `pages/` directly. `promote` is the only writer.

## Hard rules

- Never autonomously invoke `/wiki-capture` mid-session. Wait for the user.
- Never edit files under `/Users/diegovaille/Git/wiki/<project>/pages/` by hand.
- Never edit `/Users/diegovaille/Git/wiki/<project>/views/*.md` — they are regenerated by `WIKI index`.
- For `/wiki-capture`, propose at most ONE canonical change.
- If the session has no material wiki-worthy content, propose `action: noop` and stop.
